Service-Provider Dashboard — Logs / Activity module

Proposed new section for the web provider dashboard: a filterable activity & audit log covering the booking lifecycle, OTP lock-box access, payments, fleet edits, staff sign-ins and branding changes. Wireframe fidelity — layout and behaviour, not final pixels.

Fidelity & honesty note. The dashboard shell (sidebar: Overview · Fleet · Branches · Bookings · Branding, language switch, log out) is drawn from the live apps/dashboard DashboardLayout.tsx — that is the real current state, and it has no Logs item today. Everything inside the Logs section is net-new: there is currently no audit/log module in apps/api (modules today are auth, bookings, payments, fleet, notifications, contract, otp, realtime, health). Colours use the deck's wireframe tokens (orange accent); the real dashboard theme is per-provider white-label, so brand colour is illustrative only. Copy shown in English; the dashboard ships EN + AR (RTL) via react-i18next and logical-prop layout — an Arabic mirror is included in §4.

2 · Activity Log — main view NEW
A reverse-chronological, paginated table of events. Each row is colour-tagged by domain (booking · OTP · payment · fleet · auth · branding) so a provider can scan fast. Filters narrow by date range, event type, branch/actor and free-text search; Export CSV respects the active filters.
Data is provider-scoped from the auth token (never a client-supplied providerId), matching how fleetApi / bookingApi already scope reads. Times shown in the provider's locale via toLocaleString(). The status enum (confirmed → vehicle-prepared …) is the authoritative BOOKING_TRANSITIONS from @car-rental/types — the log never invents its own.

3 · Event detail — drawer NEW
Clicking a row opens a right-side drawer with the full event: who/what/when, the target entity, a before→after for state changes, and (for security-sensitive events) the request context. Shown here on the platform's core security event — an OTP lock-box unlock.
OTP detail surfaces metadata about an unlock (booking, vehicle, validity window, result, IP/device) — never the OTP code itself. This matches the product rule that OTP plaintext is bound to booking + vehicle + time window and is never logged or persisted in the clear.

5 · How an entry is created NEW
The log is written by the backend, not the client — every domain module emits an audit event on the actions that matter; the Logs screen only reads them back. This keeps the trail honest even for actions taken via API or the mobile app.
Provider / customer / system action
(accept, issue OTP, pay, edit vehicle…)
→
Domain module emits
audit.record(event)
→
Row written to
AuditLog (Postgres)
→
Logs screen queries
GET /audit-logs (filtered)
Backend impact (call-outs per project rules).
  • New API module apps/api/src/modules/audit (route → controller → service → repository), plus GET /audit-logs (filter + paginate) and GET /audit-logs/export.csv.
  • Prisma migration — new AuditLog model (see schema below). Relational FKs to provider / booking / vehicle for integrity.
  • Event hooks — existing modules (bookings, otp, payments, fleet, auth, branding) call the audit service on their mutating paths. Emitting must never block the primary action (fire-and-forget / same-transaction — a §6 decision).
  • Env vars — none new for the MVP. A retention job (cron / scheduled task) is only needed once retention policy is fixed (§6).

6 · Open decisions PENDING
These shape data model and scope — worth locking with the client/PM before build. Defaults proposed in brackets.
⏳ Awaiting client / PM input
  • Audit scope — which events to capture for v1? [booking lifecycle + OTP + payments first; fleet/branding/auth next]
  • Visibility / RBAC — can all staff see logs, or owner/admin only? Security events (OTP, sign-ins) may need a tighter role. [owner sees all; staff see non-security]
  • Retention — how long are entries kept? Drives a purge job + storage. [13 months]
  • Immutability — is this a tamper-evident audit trail (append-only, no deletes) or a convenience activity feed? [append-only]
  • Export & PII — CSV includes customer names? Mask in export / require a reason? [mask customer PII unless owner]
  • Write coupling — emit in the same DB transaction (consistent, slightly slower) or async (fast, can drop on crash)? [same transaction for money/OTP, async otherwise]
